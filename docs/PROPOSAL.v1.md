## 0. 最初に: 依頼文の前提と実データの食い違い

依頼文 §12 の「勝手に仮定せず、まず Notion の実データを確認する」に従って調査した結果、
**依頼文が想定していたデータ構造は Notion に存在しませんでした。** 先にこれを共有します。

| 依頼文の想定 | 実際の Notion |
|---|---|
| トランジション用の Notion データベース（From Track / From Cue / 評価 / 小節数 / 種類 の列） | **データベースなし。** 自由記述のネストした箇条書きページが3枚だけ |
| 各トランジションに「評価（★）」 | **評価は1件も存在しない** |
| BPM / Key / Energy | **Notion に一切なし** |
| Cue の位置情報（`01:32.450`） | **Notion になし。** rekordbox の `master.db` にのみ存在 |
| 楽曲を一意に識別する ID | **なし。** 略称・表記ゆれのある曲名テキストのみ |

### これが MVP に与える影響（要判断）

- **MVP項目7「評価を表示」は、現状そのままでは実現できません。** 表示すべきデータが無いためです。
  → スキーマ上は `rating` を nullable で用意し、記録方法が決まるまで UI に出さない、を提案します（§8 で選択肢を提示）。
- 将来機能の「評価順フィルタ」「評価の高いトランジションだけ表示」も同じ理由で保留になります。
- 「BPM条件フィルタ」「Key条件フィルタ」は **rekordbox 連携が前提** になります（Notion 側には無いため）。

それ以外の MVP 項目 1〜6, 8〜10 は、現データのままで実現可能です。

## 1. 現在の Notion データ構造（実地調査の結果）

### ページ階層

```
Interests / Music / ボカロ
  └─ (inline DB) → ボカロDJ                     ← 分類つきメモ + Appendix 生ログ
       └─ (inline DB, プロパティは Name のみ)
            ├─ 完全版                            ← ★実質的なメインデータ
            └─ キュー振り                        ← キュー命名の語彙定義
```

- URL（メイン）: 作者の Notion ページ（「完全版」）
- 内包する DB のプロパティは **`Name`（タイトル）1つだけ**。構造化された列は存在しません。

### 「完全版」の記法（一貫性が高い）

```
1. **ベノム → ドーナツホール**
   - ベノム：F「助走 1サビ終受け 」
   - ドーナツホール：B「イーイー」
     1. **分岐：ドーナルホール → 転生林檎**
        - ドーナルホール：F「サビ終」ループ
        - 転生林檎：C「1番入前」ループ
```

読み取れる規則:

| 要素 | パターン | 例 |
|---|---|---|
| エッジ見出し | `**{曲A} → {曲B}**` | `ベノム → ドーナツホール` |
| Cue 参照 | `{曲名}：{英字}「{キュー名}」{修飾}` | `ドーナツホール：F「サビ終」ループ` |
| キュー名 | `「」` の中身 | ✅ **こちらが正**（§2.1） |
| Hot Cue 記号 | `A`〜`H` | ⚠️ **rekordbox 実機とズレている可能性あり**（§2.1） |
| 修飾語 | `ループ` / `16小節前` / `1小節前` / `1.1bars` / `ラストビート付近` | |
| メモ | `- → …` 行 | `→ 同時に流して切り替え` |
| 連鎖 | 番号付きリストの連番 = チェーン（1→2→3） | |
| 分岐 | ネストした `**分岐：…**` | |

### 「キュー振り」= キュー命名の語彙（rekordbox 側と共通）

`歌入` / `1サビ` / `1サビ終` / `2歌入り` / `2サビ` / `大サビ` / `ラス受け`
`1サビ終ループ` / `受終` / `ドロップ` / `受け` / `助走`

→ **この語彙が、Notion と rekordbox を突き合わせる鍵になります**（§4）。

### 現在のデータ量（実測）

- 「完全版」: 6チェーン / **15エッジ** + 分岐1 + 未整形メモ2行
- 「ボカロDJ」: 分類済み 6エッジ + Appendix 生ログ 約15行（多くは完全版と重複）
- 重複排除後: **ユニークなトランジション 約25本 / 楽曲ノード 約25曲**

> 補足: 「ボカロDJ」ページには `## 1.` と `## 4.` の見出しはあるが `2.` `3.` が無く、区切り線だけが残っています。
> 削除済みなのか記入予定なのか、確認させてください（メインデータは「完全版」なので MVP には影響しません）。

## 2. 最大のリスク: 楽曲の同一性（Track Identity）

**ここが失敗すると、コア機能である「A→B→C と辿る」が静かに壊れます。**
A→B の B と、B→C の B が別ノードとして扱われると、チェーンが繋がらないためです。

実データで確認できた表記ゆれ:

| Notion 内の表記 | 正 | 種別 |
|---|---|---|
| `ドーナルホール` | ドーナツホール | 誤字 |
| `Rabit Hole` | Rabbit Hole | 誤字 |
| `マーシャル` / `マーシャマキシマイザー` | マーシャル・マキシマイザー | 略称・誤字 |
| `アイドル` / `Idol` | 同一曲 | 日英ゆれ |
| `ヴァンパイア` / `Vampire` | 同一曲 | 日英ゆれ |
| `バットアップル` / `BAD APPLE!!` | 同一曲 | 表記ゆれ |
| `脳漿` / `脳漿炸裂ガール` | 同一曲 | 略称 |
| `ダイダイダイダイキライ` | ファイル名は `ダイダイダイダイダイキライ`（ダイが1つ多い） | 表記ゆれ |
| `ビビデバ` | `星街すいせい - ビビデバ (NAMA FULLCORE remix).wav` | 略称 vs ファイル名 |
| `メズマライザー` | `Mesmerizer (Newlisk Frenchcore Remix).mp3` | 日英ゆれ |
| `ローリンガール` | `rolling girl remix.wav` | 日英ゆれ |

### 対策（設計の中核）

1. **正準IDは rekordbox の Track ID にする**（Notion の曲名ではなく）。
   依頼文 §12-10「将来的な Rekordbox 連携を妨げないデータ設計」が実質的に要求しているのはこれです。
2. rekordbox 連携が繋がるまでは **安定 slug + 明示的なエイリアス表** を使い、**一度だけ**確認していただく。
3. **未解決の曲名は、勝手に新しいノードを作らず、パースエラーとして画面に出す。**
   （静かにノードが増殖するのが最悪のパターンなので、必ず可視化します）
4. 曲名の照合は **日英どちらからも引ける** ようにします（`ローリンガール` ⇄ `rolling girl remix.wav`）。
   自動一致は「候補提示」までとし、**確定は必ず人のレビューを通します**（自動確定は事故のもとなので）。

## 2.1 Cue の解決: 「」内のキュー名が正、アルファベットは信用しない

**（ご指摘を反映）** `ドーナツホール：F「サビ終」` において、

- **`「サビ終」` = 正準。** これが真の識別子
- **`F` = 参考値。rekordbox 実機とズレている可能性がある**

したがって設計を次のようにします。

| | 扱い |
|---|---|
| **キュー名（「」内）** | **一次キー。** これで rekordbox のホットキュー名にマッチさせる |
| **アルファベット（A〜H）** | 補助ヒント。同名キューが複数ある場合のタイブレークにのみ使用 |
| **不一致時** | エラーにせず「rekordbox 実機では **D**（Notion は F）」と **両方を並べて表示** |

**なぜこれが重要か:** DJ 中に実際に押すのは **アルファベットのボタン** です。
つまり「Notion の記号が信用できない」＝「MVP 単体では、押すべきボタンを断言できない」ことを意味します。
これは rekordbox 連携を「あると嬉しい」から **「正しい記号を出すための必須要件」** に格上げします（§8 Q3 で再検討）。

MVP 段階では、記号は `F?` のように **不確実マーク付き** で出し、キュー名を主役にします。
rekordbox を繋いだ時点で `?` が取れ、ズレていた分は自動で訂正されます。

**副次的な効果:** キュー名で照合するため、「キュー振り」ページの語彙
（`歌入` `1サビ終` `助走` `受け` `ドロップ` …）が、そのまま突き合わせの辞書になります。

## 3. データモデル

```ts
// 楽曲ノード
type Track = {
  id: string;              // 正準ID。将来 rekordbox の ID に置換可能な安定slug
  name: string;            // 正準名（表示用）
  aliases: string[];       // Notion 内の表記ゆれを全部ここに寄せる
  artist?: string;         // Phase 2: rekordbox から
  bpm?: number;            // Phase 2: rekordbox から
  key?: string;            // Phase 2: rekordbox から
  rekordboxId?: string;    // Phase 2
  filePath?: string;       // Phase 2
};

// Cue（Phase 2 で rekordbox から充填。MVP では参照だけ持つ）
type Cue = {
  trackId: string;
  kind: 'hot' | 'memory';
  letter?: 'A'|'B'|'C'|'D'|'E'|'F'|'G'|'H';  // Hot Cue
  number?: number;                            // Memory Cue
  name: string;                               // 「1サビ終」等
  positionMs?: number;                        // Phase 2: rekordbox のみが持つ
};

// トランジション内の Cue 参照（Notion から取れる情報だけ）
type CueRef = {
  raw: string;                 // 元テキスト（常に保持。デバッグと信頼性のため）
  cueName: string;             // ★一次キー。「」の中身。'サビ終'
  letterInNotion?: string;     // 'F' — あくまで Notion 上の記載。正しいとは限らない
  modifier?: 'loop' | 'barsBefore' | 'nearEnd' | 'fromStart';
  bars?: number;               // 16小節前 → 16
  resolvedCue?: Cue;           // Phase 2: cueName で rekordbox から解決
  letterConflict?: boolean;    // rekordbox の実記号と letterInNotion がズレていた
};

// エッジ
type Transition = {
  id: string;
  fromTrackId: string;
  fromCue: CueRef;
  toTrackId: string;
  toCue: CueRef;
  technique?: 'simultaneous' | 'loopMatch' | 'cut' | 'beatToBeat';  // メモから導出
  note?: string;               // 「同時に流して切り替え」等
  rating?: number | null;      // 現状は常に null（§0 参照）
  chainId?: string;            // 依頼文の「A→B→E→G」を素直に表現
  chainPos?: number;
  branchOfTransitionId?: string;  // 「分岐：…」を保持
  source: { pageId: string; pageTitle: string; blockPath: string };  // Notion へ戻れる
};

// チェーン（記録済みの実績ルート）
type Chain = { id: string; label: string; trackIds: string[]; sourcePageId: string };
```

**設計上のポイント**: `完全版` は単なるエッジ列ではなく **番号付きの連鎖（実際に回した順序）** を記録しています。
これはフラットなエッジ集合より情報量が多く、依頼文の「A→B→E→G を辿る」に直結します。
そのため `chainId` / `chainPos` / `branchOf` を **エッジと併存させて保持** します（フラット化しません）。
また `技術種別` と `小節数` は、勝手に新設するのではなく **既存の修飾語から導出** します。

## 4. アーキテクチャ

### 方針: MVP で新しい DB は作らない

依頼文 §10「最初から不要なデータベース構築を増やさないこと」に従い、**Supabase は MVP では使いません。**
現在 25エッジ規模であり、DB を挟む理由がありません。

```
Notion API (@notionhq/client)
    ↓ ページのブロックツリーを取得
パーサ (TypeScript, 純関数・単体テストあり)
    ↓ Track / Transition / Chain に変換 + エイリアス解決
エイリアス表 (data/aliases.json — 人がレビュー可能)
    ↓
グラフスナップショット (JSON, サーバ側でメモリキャッシュ)
    ↓
Next.js App Router (Server Components) → Vercel
```

- **Next.js 15 (App Router) + TypeScript + Tailwind CSS**
- **ホスティング: Vercel**（依頼文の候補どおり。無料枠で足ります）
- **キャッシュ**: `unstable_cache` + ISR（revalidate 600秒）。
  Notion 更新後すぐ見たい場合のために **「同期」ボタン**（保護された Route Handler → `revalidatePath`）を用意
- **フォールバック**: パース失敗時は `data/snapshot.json`（リポジトリにコミット済みの直近正常データ）を使い、
  **DJ 中に画面が真っ白になることを防ぎます**
- **認証**: 個人利用のため MVP では不要。Vercel の Deployment Protection で十分

### 将来の Rekordbox 連携を妨げない設計

`master.db` は SQLCipher 暗号化されていますが、`pyrekordbox` 等で復号読み取り可能です（未インストール）。
Phase 2 では **ローカルで実行するエクスポータ**（`master.db` をコピーしてから読む。
※ rekordbox 起動中の実ファイルは 4MB の `-wal` があるため直接読まない）が
`tracks.json` / `cues.json` を吐き、それをアプリが取り込む形にします。
アプリ側は最初から `rekordboxId` / `bpm` / `key` / `positionMs` の口を持っているので、**差し替えるだけ**で繋がります。

## 5. 画面構成（DJ 中に使える UI 優先）

### ① `/` — 楽曲一覧・検索
- インクリメンタル検索（正準名 **とエイリアス両方**にヒット。「脳漿」で「脳漿炸裂ガール」が出る）
- 各曲に「出ていける本数 / 入ってこれる本数」バッジ
- 直近に見た曲を上部に

### ② `/track/[id]` — ★最重要画面「今この曲を流している」
モバイルで上から順に、依頼文 §11 のとおり:

```
┌─────────────────────────┐
│ 🎵 ドーナツホール          │  ← 現在の曲（大きく固定ヘッダ）
│    128 BPM · 8A          │     ※BPM/Key は Phase 2
├─────────────────────────┤
│ 次に行ける曲              │
│                          │
│ ▸ ローリンガール          │  ← カード。タップで遷移
│   「サビ終」 ループ  [F?]  │  ← キュー名が主役／記号は不確実マーク付き
│        ↓                 │
│   「ピアノ前 ビート」 [B?] │
│   💬 —                   │
│                          │
│ ▸ 転生林檎        (分岐)  │
│   「サビ終」 ループ  [F?]  │
│        ↓                 │
│   「1番入前」ループ  [C?]  │
└─────────────────────────┘
```
（rekordbox 接続後は `[F?]` → `[D]` のように確定表示になり、ズレていた場合は `[D] ⚠Notion:F` と併記）
- **キュー名（「」内）を一番大きく** 表示。ここが唯一信頼できる識別子のため
- 「← 入ってこれる曲」も折りたたみで持つ（逆引き）
- 画面上部に **パンくず** `ベノム → ドーナツホール → ?` を表示し、URL に `?path=` で保持
  → リロードしても、DJ 中の文脈が消えません

### ③ `/chain` — 記録済みチェーン一覧
「完全版」の 6 チェーンをそのまま並べる。実績のあるセットの流れをそのまま見られる

### ④ `/health` — パース状態（開発・運用用）
未解決の曲名、パースできなかった行、エイリアス候補を一覧表示。
**Notion に新しい繋ぎを書いたとき、拾えているかをここで確認できます**

### ⑤ `/graph` — Phase 2
Cytoscape.js。全体表示ではなく「選択曲から N ホップ」を既定にします

### UI 方針
- **ダーク基調**（DJ ブースは暗いため）、コントラスト高め
- タップ領域を大きく、スクロールなしで「次の候補」上位3件が見える
- 情報の優先順位: `曲名 > Cue記号 > Cue名 > 修飾(ループ/小節) > メモ`

## 8. 確認したいこと（3点）

### Q1. 評価（★）をどうしますか？ — **これだけは判断が必要です**

- **(A) 推奨:** Notion のメモ行に `★4` と書き足す運用にする。パーサが拾います。
  記法を変えずに済み、過去分は書いたものから順に反映されます
- (B) アプリ側で評価を付けられるようにする（要 DB。MVP の「DB を増やさない」方針とは衝突）
- (C) MVP から評価を外し、Phase 2 に送る

### Q2. Notion の書き方（型が未確定とのことなので、こちらから提案します）

- **(A) 推奨: 今の自由記述を維持 + 最小限の記法だけ揃える。**
  具体的には「**曲名は毎回フルネームで書く**」「**キュー名は必ず `「」` で囲む**」の2つだけ。
  記入速度はほぼ落ちず、パーサの精度が大きく上がります。表記ゆれは既存分もエイリアス表で吸収します
- (B) Notion を構造化 DB に移行（列: From Track / From Cue / …）。
  ドロップダウンで曲を選ぶので表記ゆれは根絶できますが、DJ 練習後にサッと書く速度は落ちます
- ※ どちらを選んでも **パーサは既存25本の移行に必要** なので、(A) の作業は無駄になりません

### Q3. rekordbox 連携をいつ繋ぎますか？（★ご指摘を受けて推奨を変更しました）

「アルファベットがズレている可能性がある」＝ **MVP 単体では押すべきボタンを断言できない**ため、
当初案の「Phase 1.5」から前倒しを推奨します。

- **(A) 推奨: Phase 1 と並行。** Notion だけの MVP をまず動かしつつ、
  すぐに rekordbox エクスポータを繋いで **記号を確定させる**。BPM / Key / Cue位置も同時に入ります
- (B) 当初案どおり MVP を完全に出し切ってから接続（記号は当面 `F?` 表示のまま）

**「Q1 は A、あとは提案どおりで」で完全な回答になります。** その場合すぐ Phase 0 に着手します。
