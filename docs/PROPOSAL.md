## 2. 実データ検証の結果（実証済み）

### 2.1 rekordbox は読めます

`~/Library/Pioneer/rekordbox/master.db` は SQLCipher 暗号化ですが、`pyrekordbox` で復号読み取りに成功しました。

- **70曲 / 507キュー**を取得。うち DJ_songs 配下が約50曲
- 取得できた項目: `曲名` `アーティスト` `BPM` `Key` `ファイルパス` `rekordbox内部ID`
- キューごとに: `種別(Hot/Memory)` `記号(A〜P)` `キュー名` `位置(ms)` `ループ長` **`UUID`**
- ※ rekordbox 起動中は `master.db-wal` があるため、**必ずコピーしてから読みます**（実ファイルは触りません）

### 2.2 「」内のキュー名は完全に信頼できます

Notion の `ベノム：F「助走 1サビ終受け 」` に対し、rekordbox 側のキュー名は
`'助走 1サビ終受け '` — **末尾の半角スペースまで完全一致**しました。ご指摘のとおりです。

### 2.3 アルファベットは信頼できません（実測）

Notion の全キュー参照27件を rekordbox に突き合わせた結果:

| マッチ厳密度 | 件数 | 備考 |
|---|---|---|
| キュー名が完全一致 | **14** | 最も信頼できる |
| 前方一致 | 7 | `イーイー` → `イーイービート` 等 |
| 部分一致（要人確認） | 3 | 誤マッチの可能性あり |
| 一致せず | 3 | §2.5 |

**完全一致した14件のうち、記号が一致したのは5件だけ。残る9件はズレていました。**

| Notion | rekordbox 実機 | キュー名 |
|---|---|---|
| ベノム **F** | **G** | 助走 1サビ終受け |
| ローリンガール **I** | **J** | 受け |
| パンダヒーロー **D** | **E** | 1サビ終 |
| ラグトレイン **G** | **H** | ラス受け |
| BAD APPLE!! **A** | **B** | 1.1Bars |
| モザイクロール **E** | **F** | 助走 1サビ終受け |
| 脳漿炸裂ガール **E** | **F** | 助走ドロップ 1サビ終受け |
| メルト **H** | **I** | 助走 受け |
| アイドル **E** | **F** | 助走 受け |

**9件すべてが「+1」（Notion が実機より1つ手前）です。** 偶然ではありません。
`Documents/rekordbox/CueConv/` に 8/8 と 8/11 の「メモリーキュー→ホットキュー変換」ログが残っており、
**この変換で記号が繰り下がったのに、Notion のメモが変換前のままになっている**のが原因と考えられます。

> つまり、**今の Notion のメモを見ながら DJ すると、約6割の場面で違うパッドを押すことになります。**
> これが、rekordbox 連携を「あると嬉しい」ではなく必須と判断した理由です。

### 2.4 曲名の同定は、キュー名が解いてくれます

Notion の略称に対し rekordbox 側に**複数候補**があるケースが実在しました:

- `メルト` → `メルト(CPK! Remix)` と `メルト (Nurecha bootleg Remix)` の2件
- `転生林檎` → `ピノキオピー - 転生林檎(HardTecno)` と `転生林檎_over-Ringo-remix` の2件
- `Rabbit Hole` → `rabbit_hole_kcboot` と `Deco27 - Rabbit Hole (Bemax Remix)` の2件
- `ダイダイダイダイダイキライ` → `(PiEa Bassline Garage remix)` と `_ Fine Day Anthem` の2件

**キュー名が曖昧性を解消します。** 例: Notion の `メルト：H「助走 受け」` は、
`メルト(CPK! Remix)` にはキュー名が付いていないため、`メルト (Nurecha bootleg Remix)` に一意に確定できました。

### 2.5 解けなかった3件（正直な数字として）

`ローリンガール B「ピアノ前 ビート」` / `アイドル E「ラスト緑CHORUS 1のビート」` /
`Rabbit Hole B「ヤァヤァヤァヤァ」` の3件は、rekordbox 側に対応する名前がありません
（実機は ` ビート ピアノ前` のように**語順違い**、または後からキュー名を変更した可能性）。
→ これらは **移行時に手動で対応付けていただく想定**です。3件なら現実的な手間です。

## 3. データモデル

正準IDは **rekordbox の内部ID**、キューの正準IDは **rekordbox の UUID** とします。
依頼文 §12-10「将来的な Rekordbox 連携を妨げないデータ設計」への回答です。

```ts
type Track = {
  id: string;            // = rekordbox ContentID（正準）
  title: string;         // rekordbox のフルタイトル
  displayName: string;   // 表示用の短縮名（「ベノム」等・人が設定）
  aliases: string[];     // Notion の旧表記を吸収（移行用）
  artist?: string; bpm: number; key?: string; filePath: string;
};

type Cue = {
  uuid: string;          // = rekordbox キューUUID（正準・差分検出の要）
  trackId: string;
  kind: 'hot' | 'memory';
  letter?: string;       // 'A'〜'P'。★rekordbox が唯一の正
  name: string;          // 「助走 受け」等。★人が読む識別子
  positionMs: number;
  loopBars?: number;
};

type Transition = {
  id: string;            // Notion page id
  fromTrackId: string; fromCueUuid: string;
  toTrackId: string;   toCueUuid: string;
  comment?: string;
  technique?: string;    // 任意: 同時流し / ループ合わせ / カット
  bars?: number;         // 任意: 16小節前 等
  rating?: number|null;  // Phase 2。MVP では未使用
  chainId?: string; chainPos?: number; branchOfId?: string;
  syncStatus: 'ok' | 'needsReview';   // §6
};
```

**チェーンを保持する理由:** 「完全版」は単なるエッジ集合ではなく、
**実際に回した順序（1→2→3）と分岐**を記録しています。これはエッジ集合より情報量が多く、
依頼文の「A→B→E→G を辿る」に直結するので、フラット化せず `chainId` / `chainPos` として保持します。

## 4. Notion の構成（★Q2 のご要望を形にしたもの）

「2曲 + 2キューを選んで一言」を最短手数で実現するため、**DBを3つ**に分けます。

```
🎵 Tracks DB   ← rekordbox から自動生成・自動更新（人は触らない）
📍 Cues  DB   ← rekordbox から自動生成・自動更新（人は触らない）
🔀 Transitions DB ← ★ここだけに人が書き込む
```

### 🔀 Transitions DB（入力するのはここだけ）

| プロパティ | 型 | 必須 | 備考 |
|---|---|---|---|
| **From 曲** | リレーション → Tracks | ✅ | |
| **From キュー** | リレーション → Cues | ✅ | |
| **To 曲** | リレーション → Tracks | ✅ | |
| **To キュー** | リレーション → Cues | ✅ | |
| **コメント** | テキスト | | 「同時に流して切り替え」等 |
| 種類 | セレクト | | 同時流し / ループ合わせ / カット / ビート合わせ |
| 小節数 | 数値 | | |
| 評価 | セレクト | | **Phase 2 用。既定ビューでは非表示にします** |
| 同期ステータス | セレクト | | 自動更新（§6）。`OK` / `要確認` |

### 入力が速くなる仕掛け: Cues DB のタイトル設計

Notion のリレーション選択は**タイトルの部分一致で絞り込める**ため、Cues のタイトルをこうします:

```
ベノム / G「助走 1サビ終受け」
ドーナツホール / B「イーイービート」
メルト (Nurecha) / I「助走 受け」
```

→ 「From キュー」欄で **`ベノム` と打てば、その曲のキューだけが並びます。**
曲を選んだ後にキューを選ぶ、という自然な流れで、**タップ数はほぼ最小**です。

### これが「記号ズレ」を根本から消します

選択肢そのものが rekordbox 実データから生成されるので、
**新しく書くトランジションでは、記号が間違いようがありません。**
既存25本のズレは移行時に一括修正します（§6 の承認フローを通します）。

> Tracks / Cues DB は機械が管理する「鏡」です。手で編集すると次回同期で上書きされるため、
> 説明文にその旨を明記し、既定ビューは読み取り前提のレイアウトにします。

## 5. アーキテクチャ

```
[ローカル Mac]
  rekordbox master.db (SQLCipher)
      │ ① コピーして復号読み取り（pyrekordbox）
      ▼
  エクスポータ + 同期CLI  ──②差分検出＆承認──▶  あなた
      │ ③ 承認された分だけ書き込み
      ▼
[Notion]  🎵Tracks / 📍Cues / 🔀Transitions
      │ ④ Notion API で読み取り
      ▼
[Vercel]  Next.js App Router（読み取り専用）→ スマホ / PC
```

**重要な制約:** `master.db` はこの Mac にしかないため、**rekordbox 連携は必ずローカル実行**になります。
Vercel 上のアプリは Notion を読むだけの読み取り専用にし、責務を分けます。

- **Next.js 15 (App Router) + TypeScript + Tailwind CSS / ホスティング: Vercel**
- **MVP では Supabase を使いません**（依頼文 §10 の方針どおり。約25エッジ規模で DB を挟む理由がないため）
- Notion 取得は ISR（revalidate 600秒）+ 手動「同期」ボタン
- **フォールバック:** 取得失敗時は最後に成功したスナップショットを表示し、**DJ 中に画面が落ちないようにします**
- 認証: 個人利用のため MVP では不要（Vercel Deployment Protection で十分）

## 6. ★同期レビュー機能（追加ご要望）

> 「rekordbox でキューを色々変えるので、その度にズレを確認して承認を求めてほしい」

### 推測ではなく、厳密な差分検出でやります

rekordbox のキュー行は **UUID を持っています**。これを Notion の Cues DB に保存しておけば、
「名前が似ているから同じキューだろう」という推測は一切不要になります。

`pnpm sync` を実行すると、前回スナップショットと現在の rekordbox を UUID で突き合わせ、
変化を4種類に分類します。

| 検出 | 判定 | 提示のしかた |
|---|---|---|
| UUID同一・**記号が変化** | 自動修正の提案 | 「`ベノム「助走 1サビ終受け」` は **F → G** に変わりました。更新しますか？」 |
| UUID同一・**キュー名が変化** | 自動修正の提案 | 「`「サビ終」` → `「1サビ終」` に改名されています。更新しますか？」 |
| UUID同一・**位置が変化** | 通知のみ | 「位置が 1:32.450 → 1:33.100 に移動（記号・名前は同じ）」 |
| **UUID が消えた** | ⚠️ 要判断 | 「このキューは削除されました。**これを使うトランジション3件**をどうしますか？」 |
| **新しい UUID** | 情報 | 「新しいキューが5件追加されました」 |

### 承認フロー（勝手に書き換えません）

```
$ pnpm sync

⚠ 3件の変更が、既存のトランジションに影響します

 [1/3] ベノム「助走 1サビ終受け」
       記号:  F  →  G
       影響:  ベノム → ドーナツホール
       [y] 更新する  [n] そのまま  [s] 保留  [d] 詳細
```

- **承認された分だけ** Notion に書き戻します。既定は「何もしない」です
- 保留にしたものは Notion 側の `同期ステータス = 要確認` に立ち、
  **アプリのトランジションカードにも「⚠ 要確認」バッジが出ます** → スマホでも気づけます
- 承認履歴は残すので、後から「いつ何が変わったか」を追えます

**最初の実行が、そのまま既存9件の記号ズレの一括修正になります。**

## 7. 画面構成（DJ 中に使える UI を優先）

### ① `/` — 楽曲一覧・検索
- インクリメンタル検索（フルタイトル・短縮名・旧表記のすべてにヒット。「脳漿」で当たります）
- BPM / Key を併記（rekordbox から入るので MVP から表示できます）
- 「出ていける本数 / 入ってこれる本数」バッジ

### ② `/track/[id]` — ★最重要画面「今この曲を流している」

```
┌──────────────────────────────┐
│ ドーナツホール                  │ ← 固定ヘッダ
│ 130.0 BPM · Bm                │
├──────────────────────────────┤
│ 次に行ける曲                    │
│                               │
│ ▸ ローリンガール    200.0 · Bm  │ ← タップで遷移
│   ┌───┐                       │
│   │ F │ 「1サビ終」 ループ       │ ← 記号を大きく（rekordbox 確定値）
│   └───┘   1:34.285            │
│      ↓                        │
│   ┌───┐                       │
│   │ B │ 「ビート ピアノ前」      │
│   └───┘   0:11.999            │
│   💬 8小節使って繋ぐ            │
└──────────────────────────────┘
```

- **記号（A〜P）を一番大きく。** DJ 中に押すのがこれだからです。
  rekordbox 由来の確定値のみ表示し、未同期・要確認のものには `⚠` を付けます
- キュー位置（`1:34.285`）も出す — rekordbox から取れるため
- 「← 入ってこれる曲」も折りたたみで（逆引き）
- **パンくず** `ベノム → ドーナツホール → ?` を URL (`?path=`) に保持
  → リロードしても DJ 中の文脈が消えません
- BPM 差を色分け（±3% 以内なら緑、等）— rekordbox の BPM があるため MVP から可能

### ③ `/chain` — 記録済みチェーン一覧
「完全版」の6チェーンをそのまま。実績あるセットの流れを再現できます

### ④ `/health` — 同期状態・要確認一覧
記号ズレ、未解決の曲名、削除されたキューを参照しているトランジションを一覧表示

### ⑤ `/graph` — Phase 2
Cytoscape.js。全体表示ではなく「選択曲から N ホップ」を既定にします

### UI 方針
ダーク基調（DJブースは暗い）／タップ領域大きめ／スクロールなしで次の候補が3件見える／
情報優先度は `曲名 > 記号 > キュー名 > 修飾 > コメント`

## 10. 確認したいこと

**Notion ワークスペースに新しく DB を3つ作る**ことになるので、着手前に確認させてください。

1. **作成場所**: 「ボカロDJ」ページ配下に作る想定です（既存の「完全版」はアーカイブとして残します）。
   別の場所がよければ教えてください
2. **既存の「完全版」ページ**: 移行後も**消さずに残します**。よろしいでしょうか
